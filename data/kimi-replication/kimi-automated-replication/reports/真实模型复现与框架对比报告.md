# 真实模型复现报告：Repair-Loop 实战 + 双框架对比

**日期**：2026-07-19　**模型**：Qwen/Qwen3-8B（SiliconFlow 真实 API）　**协议**：复刻论文 Stage B v5.4（受控状态变异，5 扰动条件 × 8 重复 = 40 运行）

---

## 一、头条结果

**从 0/40 到 40/40，靠的是 4 轮 repair-loop，而不是换模型。**

| 迭代 | 严格通过率 | 关键动作 |
|---|---|---|
| v1（初始契约） | **0/40** [0.000, 0.088] | 真实 Qwen3-8B 首次运行，全军覆没 |
| v2 | 未完整跑（单点验证） | 修复：声明证据必须引用 E1+E2、next_action 固定枚举值、added 值逐字固定 |
| v3 | **21/40** [0.375, 0.671] | 修复：transition_record 完整结构显式声明 |

最终 Wilson 区间 **[0.912, 1.000] 与论文 v5.4 报告的数值完全一致**。LangChain 管道同协议跑出 37/40 [0.801, 0.974]（差异分析见下）。

## 二、Repair-Loop 全记录（每轮失败 → 义务 → 契约修复 → 新 known-bad）

这 4 轮迭代是论文方法论的一次真实预演，且**失败模式与论文 Stage B 的记录惊人地同构**：

**v1 → v2**：模型自作主张只引用"有用的"证据 E2（漏掉规则依据 E1）；next_action 写自然语言"请求 data_residency 的具体信息"而非固定枚举值。
→ 对照论文 Stage B v5：*"the exact expected next_action value had not been declared in the model-visible gate"* —— **同一类失败**。修复：枚举值与证据引用策略显式化。新增 KB5/KB6。

**v2 → v3**：模型把 transition_record 压平为 `{"added": "..."}`,丢掉 removed/preserved。
→ 修复：完整 JSON 结构逐字声明进契约。新增 KB7。

**v3 → v4**：两类失败——(a) 约半数运行干脆省略 residual_unknown_state 字段；(b) paraphrase 条件下模型用输入的改写名（"数据存储所在地理区域"）替代规范名。
→ 修复：字段必填声明 + "所有状态标识必须使用规范名"义务。新增 KB8/KB9。修完 4 个条件全部 8/8，paraphrase 仍 1/8。

**v4 → v5**：paraphrase 条件下 attestation 句子仍用改写名（规范名义务没声明覆盖 attestation 字段）。
→ 修复：义务显式扩展。新增 KB10。**40/40 达成。**

每一轮都通过了门 A：golden 全过 + 全部 known-bad（最终 10 个）按预期原因被拦截。**known-bad 套件从 4 个增长到 10 个，全部来自真实模型失败**——这正是论文"可靠性是攒出来的"的实证。

## 三、这次复现对论文结论意味着什么

**支持的部分：**
1. **核心机制成立**：v1 契约下 0/40 → v5 契约下 40/40，同一模型、同一温度设置区间。这直接演示了论文的中心论点——*失败更多是"义务未显式化"的系统设计问题，而非模型能力问题*。弱模型使能（weak-model enablement）在真实 8B 模型上得到验证。
2. **repair-loop 协议可操作**：观察失败→隔离义务→写入契约→固化 known-bad→门控验证，4 轮收敛，每轮失败模式都精确可归因。论文说"missing obligation can be named, added to the contract, captured as a known-bad case"——我们原样走了一遍，成立。
3. **扰动条件是有效的压力测试**：paraphrase 条件确实是最后一个被攻克的（v4 时其余 4 条件已全过，它 1/8），说明扰动设计能暴露契约表达漏洞，不是摆设。

**需要诚实标注的部分：**
1. **40/40 不等于"协议天然稳定"，而等于"修复后的契约+这个模型+这个任务"稳定**。 Wilson 下限 0.912 意味着真实失败率上限仍有 ~9%；且任务是我们自定义的单个 fixture，不是论文原版的私有 fixture。
2. **契约修复的成本真实存在**：4 轮迭代、10 个 KB、每次 40 次 API 调用——与论文未回答的"契约编写成本"问题一致，本实验也未量化人力成本。
3. **存在"评估器随模型一起修"的风险**：v1 的 attestation 检查（要求含"未改变"）本身过脆，v2 改为声明式要求——这提醒我们区分"模型失败"与"评估器缺陷"，论文对此有讨论但未给出判定流程。

## 四、双框架对比（真实运行）

| | petfishframework | LangChain |
|---|---|---|
| **严格通过率** | **40/40** [0.912, 1.000] | **37/40** [0.801, 0.974] |
| 失败条件 | 无 | paraphrase 3/8 失败（同为规范名残留问题） |
| 差异解读 | 两管道跑同一 prompt 核心；差异主要来自**运行方差**（40 样本下 37 vs 40 在统计上不可分，需配对检验）及 **temperature 设置差异**（LangChain 显式 t=0；pf 未显式设温——可复现性上应补齐） | 同左 |
| 事件审计 | 原生 session.replay() 记录 model.called 等事件 | 无原生等价物 |
| 工程结论 | **论文结论不绑定框架**：同一契约栈 + 验证器在两个独立框架上均使 8B 模型达到高契约遵循度（0.825→1.000 区间）。这正面回应了"结论是否绑定 PEtFiSh"的质疑 | 同左 |
