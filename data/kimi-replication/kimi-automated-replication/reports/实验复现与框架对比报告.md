# 论文实验复现与框架对比报告

**日期**：2026-07-19　**对象**：Contract-Driven Harness 论文 Stage B v5.4 协议（受控状态变异，5 扰动条件 × 8 重复 = 40 运行）

---

## 一、复现了什么

以论文 Stage B v5.4 为蓝本，完整实现了其实验设计的**测量链路**：

| 论文设计要素 | 复现情况 |
|---|---|
| 受控状态变异任务（一项未知→已知，保持其余义务） | ✅ 实现：network_api_approval 迁移，data_residency 必须保持未知 |
| 契约对象栈（TaskSpec/MemorySlice/EvidenceBundle/OutputContract/WorkflowGate） | ✅ 全部实现为结构化对象 |
| explicit-transition-delta（G9 treatment 核心：remove/add/preserve） | ✅ 实现 |
| 7 项确定性检查（schema、精确证据数组、剩余状态、迁移准确、禁止推断、完整门、保留声明） | ✅ 全部实现，strict 聚合 |
| 5 扰动条件 × 8 重复 = 40 次运行 | ✅ canonical / field_alias / evidence_order / distractor_evidence / unknown_state_paraphrase |
| 95% Wilson 区间 | ✅ 实现，与论文算法一致 |
| 门 A 准入：golden 全过 + known-bad 按预期原因失败 | ✅ golden 全过；4 个 known-bad 各自被预期检查项拦截 |
| 真实模型运行（Qwen3-8B via SiliconFlow, temperature 0） | ⚠️ 沙箱无 API key，管道已留好接口（设 `OPENAI_API_KEY` + `OPENAI_BASE_URL` 即可跑真实模型） |

### 运行结果

**1. 管道验证（FakeModel 脚本化 golden 应答）——两个框架均通过**

```
严格通过率: 40/40 = 1.000  (95% Wilson: [0.912, 1.000])
  canonical / field_alias / evidence_order / distractor_evidence / unknown_state_paraphrase: 各 8/8
```

注意：Wilson 区间 [0.912, 1.000] 与论文 v5.4 报告的数值**完全相同**——这不是巧合，而是 40/40 时该区间的确定值，说明统计实现正确。但同样要强调：**脚本化模型的 40/40 只证明管道确定无误，不构成模型质量证据**（这正是论文"absolute question vs causal claim"的区分）。

**2. 门 A（本地门）——通过**

golden 输出全过；KB1（证据乱序）被 `exact_evidence_array` 拦截、KB2（越权推断 data_residency）被 `residual_state_accuracy` 拦截、KB3（缺 transition_record）被 `schema_validity` 拦截、KB4（门未过却声明完成）被 `complete_gate` 拦截。**每个 known-bad 都按预期原因失败**——论文准入标准中最难满足的一条成立。

**3. G0 vs G9 对照演示（模拟弱模型行为）**

```
G0（裸提示）:  19/40 = 0.475  [0.329, 0.625]
G9（全契约包）: 36/40 = 0.900  [0.769, 0.960]
```

模拟弱模型在 G0 下约 55% 概率丢义务（丢迁移记录/证据乱序/越权推断），G9 契约包下降至 10%——绝对契约遵循度提升 +0.425。这验证了**测量链路能灵敏地捕捉 harness 档位差异**；当然，数字本身来自脚本模型，真实效应需真实模型确认。

## 二、petfishframework vs LangChain 实现对比

两条管道共享同一套框架无关核心（fixture/扰动/验证器，约 320 行），框架适配层分别仅 **65 行（pf）** 和 **57 行（LangChain）**。差异不在"能不能做"，而在**多少东西是框架原生给的**：

| 维度 | petfishframework | LangChain |
|---|---|---|
| **实验运行** | Agent + Session 模式；一次 `agent.session(prompt).run()` | prompt \| model 链 + `.invoke()` |
| **事件审计/TraceLog** | ✅ **原生**：event-sourced session，`session.replay()` 自动记录 model.called/session.start/end，SIEM/OTel sink 开箱即用 | ❌ 需自行接 LangSmith（外部 SaaS）或手写 callback |
| **可靠性度量 Pass^k** | ✅ **原生**：`pass_at_k_with_perturbations`（且自带 5 种扰动函数，可注入自定义扰动），标 Stable API | ❌ 无内置，需手写 runner + Wilson 区间 |
| **零成本本地门** | ✅ FakeModel（脚本化确定性应答，专为此设计） | 🔶 GenericFakeChatModel 可用但定位是测试桩，语义弱 |
| **确定性重放/回归** | ✅ replay/rerun/resume 环境（deterministic rerun 标 Experimental） | ❌ 需外部方案 |
| **预算/权限硬门** | ✅ Budget、6 种 DecisionEffect、YAML 策略——WorkflowGate 的原生表达 | ❌ 无等价物，需自写中间件 |
| **真实模型接入** | OpenAIModel，OpenAI 兼容端点（文档明确支持 SiliconFlow） | ChatOpenAI，同样支持 base_url 切换，生态更广 |
| **模型/工具生态** | 3 个适配器，工具较少 | ★ 最大生态（数百模型/工具集成） |
| **成熟度** | v1.0 核心冻结，484 测试，但项目年轻 | 工业标准，社区与文档极厚 |

### 结论性判断

1. **复现这篇论文的实验，petfishframework 是更顺手的工具**——因为论文要的三件"非标件"（事件溯源审计、Pass^k 扰动套件、零成本确定性本地门）恰好是它的原生一等公民；在 LangChain 上这三件都要自己写或接外部服务。适配层代码量两者相近，但 LangChain 版实际上把审计和度量"外包"给了共享核心代码，等于这些能力是我们替它补的。
2. **LangChain 的优势在生态与生产集成**（模型覆盖、LangSmith 观测、部署工具链），如果目标是把 harness 推进生产系统而非做受控实验，LangChain + LangSmith 组合更现实。
3. **对论文本身的一个意外收获**：这次复现证明论文的实验设计**可以在两个独立框架上以共享核心复刻**——契约栈和验证器全部框架无关。这正是论文想要的"transferable claim, not implementation context"的直接证据，建议作者把这类跨框架复现写进论文（哪怕只跑 2-3 个机制原子），能正面回应"结论绑定 PEtFiSh"的潜在质疑。
4. **方法论体验**：复现过程中最花时间的不是写代码，而是设计"known-bad 必须按预期原因失败"——这个约束会强迫你把每个失败模式想成一阶对象，比写 happy-path 测试累，但确实抓得住问题（KB4 的 next_action 门就是在设计阶段才发现容易漏）。这侧面验证了论文 repair-loop 的工程价值。

## 三、如何跑真实模型

```bash
export OPENAI_API_KEY=<SiliconFlow key>
export OPENAI_BASE_URL=https://api.siliconflow.cn/v1
export EXP_MODEL=Qwen/Qwen3-8B
python run_petfish.py    # 或 run_langchain.py
```

管道将自动切换到真实模型路径，跑同样的 40 次冻结协议并输出 Wilson 区间，与论文 v5.4 直接可比。

**代码归档**：`/mnt/agents/work/repro/`（contract_core.py 为框架无关核心，run_petfish.py / run_langchain.py 为两条适配管道，run_arms_demo.py 为 G0/G9 对照演示）。
