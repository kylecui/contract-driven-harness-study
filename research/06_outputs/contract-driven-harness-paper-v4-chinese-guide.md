# 《面向可靠低成本Agent任务的契约驱动Harness工程》中文理解版

> 本文根据论文 *Contract-Driven Harness Engineering for Reliable Low-Cost Agent Tasks*的v4 humanized draft整理。
>
> 这不是逐句翻译，也不替代英文原文。它保留论文的研究问题、实验数据、结论边界和主要方法，用中文重新组织，目的是降低阅读成本。

## 先说结论

这篇论文研究的不是“如何把小模型变成大模型”，而是一个更窄、更工程化的问题：

> 对于输入、输出和可靠性要求都比较明确的Agent任务，能否把一部分原本依赖模型自行记忆和判断的要求，改写成外部可检查的契约，从而让低成本模型更稳定地完成任务？

论文给出的答案是：

1. **在受限、契约关键的任务中，可以。** 当任务状态、允许使用的证据、输出字段、阶段门和验证规则都被明确表示时，Qwen3-8B这类低成本模型可以达到预先声明的通过标准。
2. **这种提升不等于模型能力整体提升。** Harness减少的是任务执行中的隐式负担，没有让弱模型普遍等价于强模型。
3. **模型差距压缩只在部分任务中成立。** 高度结构化的信息抽取表现最明确；项目初始化和研究工作流中的结果则有改善、无变化和反向变化。
4. **论文最稳定的发现不是“差距消失”，而是“弱模型可用性提高”。** 只要任务边界足够清楚，外部契约可以提高低成本模型在关键操作上的可用下限。
5. **40/40通过是一个受限稳定性结果。** 它证明冻结后的某个状态变更协议在五类预设扰动下重复成功，不证明任意Agent工作流、任意状态机或生产环境都可靠。

## 1. 论文在解决什么问题

Agent执行项目初始化、结构化抽取、证据综合、计划更新或多步协作时，经常出现以下问题：

- 漏掉必须字段；
- 忘记前一步已经确认的状态；
- 把未知状态写成已知事实；
- 引用了不允许使用的证据；
- 跳过阶段门，过早给出建议；
- 输出格式正确，但结论没有证据支撑；
- 单个步骤都能通过，组合后却丢失跨步骤约束。

这些问题通常会被直接归因于模型不够强。论文认为，这种判断只说对了一部分。

模型能力当然重要。但在许多边界明确的任务里，系统在运行前已经知道哪些证据可以使用、哪些状态仍然未知、哪些字段必须输出、哪些动作被禁止、什么时候不能进入下一阶段。如果这些要求只存在于自然语言提示中，模型就必须一边生成，一边自行恢复、记忆和执行全部约束。

论文提出的思路是：把这些要求从隐式提示中移出来，变成外部可检查的契约。模型仍然负责生成和判断，但系统负责明确边界、保存状态、检查输出和阻止不合格结果继续向下流动。

## 2. 什么是契约驱动Harness

论文中的Harness不是单个Prompt，也不只是JSON Schema。更准确地说，它是一层包围模型的可靠性工程结构。

一个完整的契约驱动Harness包含以下对象：

| 对象 | 中文理解 | 主要作用 |
|---|---|---|
| `TaskSpec` | 任务规格 | 明确目标、约束、成功条件和非目标 |
| `MemorySlice` | 有界记忆切片 | 规定本次任务可以使用、不能使用和仍然未知的上下文 |
| `EvidenceBundle` | 证据包 | 列出允许使用的证据、证据类型和来源关系 |
| `OutputContract` | 输出契约 | 规定输出结构、必填字段、引用规则和验证条件 |
| `WorkflowGraph` / stage gate | 工作流与阶段门 | 规定步骤顺序，以及哪些条件不满足时必须停止 |
| `TraceLog` | 决策轨迹 | 记录选项为什么被接受或拒绝，便于审计 |
| `ValidatorGate` | 验证门 | 用确定性规则判断输出是否通过，并拒绝已知错误 |

论文关注的不是这些对象是否“看起来完整”，而是一个可靠性要求如何经历完整生命周期：

```text
观察到失败
  -> 找到缺失的义务
  -> 把义务写进输入或输出契约
  -> 增加一个能够复现失败的known-bad样例
  -> 用本地确定性验证器建立回归检查
  -> 在真实模型上做小规模定向测试
  -> 更新证据账本和结论边界
```

这里的“义务”是论文的核心单位。它可以是“必须保留未知状态”，也可以是“每条结论必须绑定证据ID”“必须记录被拒绝选项”“不得复用陈旧上下文”。

## 3. 论文为什么不用完整工作流直接做评测

完整Agent工作流的问题太多，一个总分很难说明失败发生在哪里。

例如，项目初始化失败可能来自：

- 输出结构不符合Schema；
- 工作区状态判断错误；
- 覆盖了已有文件；
- 丢失用户限制；
- 工具调用错误；
- 阶段顺序错误。

如果只看一个“任务成功率”，这些问题会被混在一起。即使分数提高，也不容易判断究竟修复了哪个机制。

因此，论文把评测分成三层。

### 3.1 任务切片

任务切片是较宽的任务类别，包括：

- 结构化抽取；
- 项目初始化；
- 研究工作流。

这一层用来观察Harness大致在哪些任务上有效，但不直接支持普遍结论。

### 3.2 机制原子

机制原子是固定输入、单一主要机制、单一主要失败模式的最小测试单元。

一个原子要进入下一阶段，至少需要：

1. Fixture结构有效；
2. Golden output能够通过；
3. 至少一个known-bad output因预期原因失败；
4. 存在可改善空间，或者实验明确研究绝对契约遵循率；
5. 低成本模型在G8/G9下改善或达到通过线；
6. 声明与下一步骤组合时的接口。

### 3.3 已准入宏

宏是多个已通过机制的组合。论文只允许通过本地门和定向模型检查的机制进入宏。

组合时还要额外声明“跨步骤携带义务”。原因很直接：一个约束在第一个步骤出现，不代表它会自动保留到第三个步骤。

因此，论文中的宏仍然是固定输入、无工具或工具受限、可确定性评估的窄任务。完整项目初始化和完整研究工作流没有被宣布为已解决。

## 4. Harness强度与模型

论文使用不同Harness arm表示外部约束强度：

- **G0**：原始或最低约束输入；
- **G2/G3**：中间强度，用于部分机制实验；
- **G8**：包含较丰富的契约和验证要求；
- **G9**：完整数据包，包括任务规格、输出契约、证据与记忆策略、工作流要求、轨迹要求和回归检查。

真实模型实验通过SiliconFlow的OpenAI兼容接口完成：

- 低成本模型：`Qwen/Qwen3-8B`；
- 早期强模型对照：`deepseek-ai/DeepSeek-V3.2`；
- 温度：`0`；
- Prompt在执行前导出并保存；
- 每次运行保留请求、输出、验证结果、指标、事件日志、耗时、错误和重试记录。

论文测量的是“是否遵守契约”，不是开放式写作质量、创造力或人类偏好。

## 5. 论文的核心方法：从失败开始修

论文没有从一个理想化大框架出发，而是从实际失败逐步收紧契约。

修复循环包含七步：

1. 观察真实模型失败；
2. 隔离缺失的机制或义务；
3. 把义务明确写进输入和输出契约；
4. 增加或更新known-bad样例；
5. 运行本地golden/bad回归；
6. 运行定向真实模型实验；
7. 更新证据账本、结论边界和后续任务。

这个流程有两个价值。

第一，失败变得可定位。系统不再只知道“答案不好”，而是知道“未知CI状态没有保留”或“被拒绝方案缺少证据ID”。

第二，修复可以进入回归测试。相同错误一旦被写成known-bad样例，后续修改就能检查它是否再次出现。

## 6. 实验结果怎么理解

### 6.1 宽任务切片：绝对表现提高，但差距压缩不稳定

结构化抽取是最支持原始假设的任务。在G9下，所有原本非零的强弱模型差距都压缩到`0.000`。这包括任务成功、Schema有效性、工具调用正确性、人工接受度、成本效率和安全一致性。

但项目初始化没有得到同样结果：

- 任务成功差距从`0.111`降到`0.000`；
- 安全一致性差距从`0.200`降到`0.000`；
- Schema有效性差距反而从`0.250`扩大到`0.583`；
- 人工接受度和成本效率也出现负向差距压缩。

研究工作流同样是混合结果：

- 一些G0差距原本就是`0.000`，因此不存在可计算的“压缩”；
- Schema有效性差距从`0.067`降到`0.000`；
- 任务成功、人工接受度和成本效率没有形成一致的正向结果。

因此，论文放弃了“Harness普遍压缩模型差距”这一强结论，改为更保守的表述：

> Harness能够提高多类任务中的绝对契约遵循率；模型差距压缩只在基线差距非零、任务高度受限时比较明确。

### 6.2 Stage 6：机制原子让问题变得可诊断

Stage 6完成了48/48次真实模型运行。低成本模型从G0切换到G9后：

- `task_success`提高`0.576`；
- `schema_validity`提高`0.833`；
- `atom_primary_metric`提高`0.833`。

在部分契约关键指标上，低成本模型加G9甚至高于强模型加G0。这不能说明低成本模型整体超过强模型，只能说明：对于被明确拆分和约束的操作，Harness可以抵消一部分模型能力差异。

### 6.3 Stage 7p：单步都通过，不代表组合能通过

Stage 7p组合了三个已经测试过的原子：

```text
有界上下文回忆
  -> 不覆盖已有状态的行动规划
  -> 验证器修复
```

低成本模型在G8/G9下的Schema和安全指标都通过，但完整链条仍然失败。原因是系统没有把“不得复用陈旧上下文”这一负向约束明确带到后续步骤，导致`context_relevance=0.000`。

Stage 7p v2增加跨步骤保留契约后，两个模型层级在G8/G9下都通过。

这一结果支持一个重要判断：

> 机制通过是组合的必要条件，不是充分条件。跨步骤约束必须作为独立义务显式传递。

### 6.4 Stage 7r.1：针对两个具体失败收紧契约

早期实验中，低成本模型仍然在两个原子上失败：

- 引用没有绑定到具体Claim；
- 被拒绝选项缺少完整决策轨迹。

修订后的契约要求：

- 每条grounded claim必须是对象，并包含非空`evidence_ids`；
- 每个被拒绝选项必须包含证据ID；
- Trace中必须记录支持和拒绝路径。

定向的8次低成本模型运行全部通过。

这里的结论仍然很窄：更严格的输出契约修复了两个已知失败，不代表它自动修复所有证据和推理问题。

## 7. Stage 7e：论文最完整的修复循环

Stage 7e把状态清单、证据绑定、证据类型、决策轨迹和阶段门组合成一个窄的“证据到决策”宏。

它的修复过程比最终分数更重要。

### 7.1 初始版本

低成本模型G9只得到`task_success=0.714`，主要丢失：

- 完整决策轨迹；
- 阶段门。

### 7.2 v2：明确保留轨迹和阶段门

v2明确要求保留`decision_trace`、`stage_gate`和`carried_obligations`。

结果是轨迹完整性和阶段完成度全部达到`1.000`，但只有1/4完整通过。新的问题是输出遗漏了未知状态，例如：

- Git分支未知；
- CI状态未知；
- 网络/API审批状态未知。

### 7.3 v3：明确列出未知状态

v3要求保留Git、CI和网络相关未知状态，以及不得推断的字段。

严格通过数提高到3/4。剩余失败来自已知状态的证据来源被压缩成泛化标签，无法看出具体事实来自哪些证据。

### 7.4 v4：已知状态必须携带来源

v4要求每个`state_inventory.known_state[]`对象都包含：

- `state_id`；
- `fact`；
- `evidence_ids`。

一次Provider超时和一次截断输出经过重试后，4/4运行全部通过。任务成功、原子主指标、状态准确性、引用支撑、证据类型、轨迹完整性和阶段完成度均为`1.000`。

这组实验说明，可靠性修复可以逐项进行：

```text
丢轨迹
  -> 把轨迹写成必填结构
漏未知状态
  -> 明确枚举未知状态
来源被压缩
  -> 要求状态对象绑定证据ID
```

论文没有把这一过程解释为“模型学会了更多”，而是解释为“系统逐步减少了需要模型自行猜测和记忆的隐式义务”。

## 8. Stage 7-next：修复能否迁移到相邻任务

Stage 7-next把Stage 7e v4的义务迁移到一个相邻的证据约束方法计划更新任务，并增加一个新压力条件。

输出必须：

- 识别下一个允许进入的宏；
- 列出准入条件；
- 保留本地门和真实模型门；
- 明确当前不能声称什么。

本地golden样例通过，提前扩展到更大工作流的known-bad样例被正确拒绝。Qwen3-8B在G8/G9下共运行4次，所有报告指标均为`1.000`，且没有Provider错误、超时或截断重试。

这个结果支持的是“向一个紧邻的固定宏迁移”，不是向任意任务类别泛化。

## 9. Stage B：为什么40/40和因果效果是两回事

Stage B研究一个受控状态变更：把“网络API审批”从未知状态移动到已知状态，同时准确保留：

- 原始证据绑定；
- 剩余未知状态；
- 剩余禁止推断项；
- 状态变更记录；
- 完整阶段门；
- 保留证明。

### 9.1 v5：严格标准下0/4

四次运行都保留了Schema、剩余状态、变更和证明，但没有保留完全一致的证据数组。模型可见契约里还缺少精确的`next_action`期望值。

### 9.2 v5.1：捆绑修复后4/4

修订做了两件事：

1. 向模型暴露完整阶段门；
2. 把不可修改的证据绑定与可编辑文字分开。

结果变成4/4。但因为两项修改同时发生，无法知道是哪一项起主要作用，样本量也不足以证明稳定。

### 9.3 v5.2：单独检验证据绑定分离

预注册消融实验共30次：

- 证据绑定分离组：精确数组检查15/15；
- Claim耦合组：精确数组检查14/15；
- 风险差：`0.067`，低于预先设定的`0.20`工程效果阈值。

两组严格总指标都只有10/15，因为共有九次运行错误保留了一个已经失效的禁止推断项。

因此，实验不支持“仅分离证据绑定就有较大独立效果”。

### 9.4 v5.3：加入显式状态变化量

v5.3保持初始状态、最终后置条件、证据、事件、阶段门、扰动和评估器完全相同。实验组只多一个`required_transition_delta`，明确写出：

- 哪些值要删除；
- 哪些值要新增；
- 哪些值必须保留。

30次新运行的结果是：

- 显式Delta组：15/15；
- 仅精确后置条件组：13/15；
- 风险差：`0.133`；
- 预注册工程效果阈值：`0.20`；
- 精确McNemar检验：`p=0.500`。

结果方向上支持显式Delta，但没有达到预先声明的“大效果”门槛。它不能证明显式Delta具有足够大的独立因果优势，也不能证明两种方案等价。

### 9.5 v5.4：冻结协议后的40次稳定性测试

v5.4不再比较两个方案，而是提出另一个问题：

> 已经修复并冻结的显式Delta协议，在重复运行和预设扰动下能否保持高通过率？

五类条件各运行8次：

| 条件 | 通过 | 通过率 | 95% Wilson区间 |
|---|---:|---:|---:|
| 标准条件 | 8/8 | 1.000 | [0.676, 1.000] |
| 字段别名 | 8/8 | 1.000 | [0.676, 1.000] |
| 证据顺序打乱 | 8/8 | 1.000 | [0.676, 1.000] |
| 干扰证据 | 8/8 | 1.000 | [0.676, 1.000] |
| 未知状态改写 | 8/8 | 1.000 | [0.676, 1.000] |
| 合计 | 40/40 | 1.000 | [0.912, 1.000] |

所有调用都返回有效JSON，没有Provider错误，也没有重试。中位延迟为`19.500秒`，P90延迟为`22.183秒`，总Token使用量为`102,984`。

正确的解读是：

> 在冻结的显式状态变化量G9协议下，Qwen3-8B在五类预设扰动、40次新运行中完成了被测试的多数组状态变更。

不能把它写成：

> Qwen3-8B对状态机操作具有100%可靠性。

40/40描述的是这一组固定Fixture中的观测结果。95% Wilson区间的下界为`0.912`，也提醒我们“样本内没有失败”不等于“总体失败概率为零”。

## 10. 论文真正支持哪些结论

### 10.1 支持

1. 契约丰富的Harness能在多个受测场景中提高绝对契约遵循率。
2. 在高度结构化且基线差距非零的任务中，Harness可能压缩强弱模型差距。
3. 对于受限、契约关键的操作，低成本模型可以在强Harness下达到声明的通过线。
4. 机制原子有助于把宽工作流失败拆成可定位、可回归测试的义务。
5. 单个机制通过后，跨步骤义务仍需显式保留。
6. 失败驱动的修复循环可以把遗漏转成契约字段、known-bad样例和确定性验证门。
7. 冻结后的Stage B v5.4协议在五类预设扰动中表现出受限稳定性。

### 10.2 不支持

论文明确不声称：

- 低成本模型普遍等价于强模型；
- Harness总能压缩模型差距；
- 完整项目初始化已经可靠；
- 完整研究工作流已经可靠；
- 当前方案可以直接用于生产环境；
- 固定宏通过就意味着开放式工具工作流可靠；
- 显式Delta已经证明具有`0.20`以上独立因果优势；
- 一组40次实验可以证明任意状态机可靠；
- Harness后的低成本模型一定比直接使用强模型更便宜或更快。

## 11. 这篇论文与现有工作的区别

论文涉及的相邻方向包括工作流编排、结构化输出、Guardrails、声明式LM程序、Agent规格、RAG、工具调用、记忆系统和安全验证。

这些方向通常解决以下问题：

- 工作流编排：步骤如何执行、暂停和恢复；
- 结构化输出：结果是否符合Schema；
- Guardrails：如何校验、拒绝和重试；
- 声明式LM程序：如何把Prompt行为组织成程序；
- RAG与工具：如何提供外部知识和行动能力；
- 记忆系统：如何保存长程状态；
- 安全验证：如何约束政策和运行风险。

本文增加的是“义务级评测与修复”视角。它不只检查工作流是否走完或JSON是否合法，还检查：

- Claim是否绑定证据；
- 未知状态是否仍然未知；
- 被排除的上下文是否没有重新进入；
- 阶段门是否阻止了过早结论；
- 被拒绝方案是否保留了可审计轨迹；
- 一个义务能否从单步测试进入组合任务。

## 12. 局限性

### 12.1 任务边界较窄

主要宏使用固定输入、无实时工具和确定性评估。实验不包括实时检索、文件修改、外部工具执行或持续变化的工作区。

### 12.2 样本量和任务多样性有限

Stage 7e v4和Stage 7-next都只有4次定向运行。Stage B v5.4增加的是同一协议的重复次数，不是任务类别的覆盖面。

### 12.3 扰动是设计出来的

字段别名、证据顺序、干扰证据和未知状态改写都属于预设测试。实验没有覆盖任意Schema变化、对抗性证据、多次状态变更、回滚、并发更新和实时工具状态。

### 12.4 只使用一个Provider

所有Provider支持的证据来自SiliconFlow。Provider侧的批处理、硬件和服务变化不可控。要形成Provider无关结论，需要跨Provider和跨模型家族复现。

### 12.5 评估器可能过拟合已知错误

确定性验证器能稳定复现，但known-bad集合只包含已经观察到或提前想到的失败。未知失败不会自动被发现。

### 12.6 工程成本尚未完成比较

Harness需要Fixture、Schema、证据包、评估器、日志和后处理。Stage B v5.4的40次运行使用了`102,984`个Token，中位延迟为`19.500秒`。

论文没有在同一冻结任务上完整比较：

- 弱模型G0；
- 弱模型G9；
- 强模型G0；
- 强模型G9。

因此，当前证据不能说明“低成本模型加Harness”的单位成功成本一定更低。简单任务上的Harness开销甚至可能高于收益。

## 13. 对工程实践的启发

这篇论文更适合被理解为一种可靠性开发方法，而不是一个通用Agent架构。

### 13.1 先选适合契约化的任务

适合的任务通常具备以下特征：

- 输入边界明确；
- 正确输出可以结构化描述；
- 存在必须保留的状态或证据；
- 错误成本较高；
- 可以构造golden和known-bad样例；
- 可以用确定性规则检查关键义务。

开放式创作、模糊战略判断和高度探索性研究不适合被完全收紧成硬契约。过度约束可能降低强模型的灵活性。

### 13.2 不要只写更长的Prompt

如果一个要求很重要，应考虑把它变成：

- 独立字段；
- 枚举状态；
- 证据ID绑定；
- 阶段门条件；
- known-bad回归样例；
- 确定性验证规则。

重要义务只在自然语言段落里出现一次，通常不够可靠。

### 13.3 组合前先检查跨步骤义务

单个节点通过后，需要单独列出哪些信息必须传到下一步：

- 已知状态；
- 未知状态；
- 禁止推断项；
- 证据绑定；
- 被拒绝选项；
- 当前阶段；
- 下一步允许或禁止的动作。

### 13.4 把负面结果留下来

Stage 7p、Stage 7e v2/v3和Stage B v5.2没有得到最终理想结果，但它们解释了后续契约为什么这样设计。

如果只保留最终40/40，会失去最有价值的工程信息：失败在哪里、修复了什么、哪些修复没有显示出足够大的独立效果。

### 13.5 最后才扩大结论

论文的顺序是：

```text
修复失败
  -> 建立回归
  -> 小规模真实模型验证
  -> 必要时做消融
  -> 冻结协议
  -> 运行新样本
  -> 更新可声称边界
```

这比先宣布框架有效，再寻找支持案例更适合可靠性研究。

## 14. 阅读这篇论文时最重要的三个区分

### 14.1 模型能力与系统可靠性

模型负责推理和生成，Harness负责把已知要求外显、保存和检查。论文证明的是部分可靠性可以由系统工程承担，不是模型能力可以忽略。

### 14.2 绝对稳定性与独立因果效果

v5.4的40/40说明冻结协议在受测条件下稳定。v5.3没有达到预注册效果阈值，说明论文没有证明“显式Delta本身带来足够大的独立效果”。两者回答的是不同问题。

### 14.3 窄宏与完整Agent工作流

窄宏使用固定输入和确定性验证。完整工作流还要处理工具选择、权限、文件系统变化、实时数据、部分失败、用户澄清和长程状态。前者通过不能直接推出后者可靠。

## 15. 术语表

| 术语 | 中文理解 |
|---|---|
| Harness | 包围模型的任务约束、状态、验证、工作流和审计结构 |
| Contract | 可以明确表示和检查的任务义务 |
| Obligation | 输出或执行过程中必须满足的具体要求 |
| Mechanism atom | 只测试一个主要机制和失败模式的最小单元 |
| Admitted macro | 由通过准入门的机制组成的受限组合任务 |
| Golden output | 应当通过验证器的标准样例 |
| Known-bad output | 应当因指定错误被拒绝的反例 |
| Stage gate | 未满足条件时禁止进入下一阶段的门 |
| Carried obligation | 必须跨步骤继续保留的义务 |
| Evidence binding | Claim、状态或决策与具体证据ID之间的绑定 |
| Unknown state | 当前证据无法确认，必须继续标为未知的状态 |
| Transition delta | 明确列出状态变更中要删除、新增和保留的内容 |
| Gap compression | 强弱模型在某项指标上的差距被Harness缩小 |
| Weak-model enablement | 低成本模型在强Harness下达到声明的通过标准 |
| Wilson interval | 对二项通过率给出的置信区间，避免把样本通过率直接当作总体真值 |

## 结语

这篇论文最有价值的部分，不是某个模型取得了40/40，而是它展示了一条可审计的修复路径：把一次失败变成一个命名义务，把义务变成契约，把已知错误变成回归样例，再用定向实验决定结论能走多远。

当前证据支持的范围仍然有限。它说明在受限、契约关键的Agent任务中，部分可靠性可以通过模型外部的工程结构实现。它没有证明低成本模型已经能够可靠处理开放式、多工具、长时程的完整工作流。
